# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`@encharm/cws` is a native C++ WebSocket implementation for Node.js that aims to be a near drop-in replacement for the `ws` module. It is a fork of ClusterWS/cWS, which itself forked uWebSockets v0.14 (dual MIT + ZLIB license, see `LICENSE` and `src/LICENSE`). Prebuilt binaries for every supported platform/ABI are committed under `dist/bindings/` and published with the package; end users never compile.

## Commands

```sh
npm run build-ts        # lint + tsc: lib/*.ts -> dist/*.js + *.d.ts (dist JS is committed)
npm run lint            # tslint over lib/**/*.ts
npm test                # nyc + mocha, runs tests/**/*.test.ts via ts-node (loads ../lib, not dist)
npx mocha -r ts-node/register tests/server-client.test.ts -g "ping/pong" --exit   # single test
npm run build-cpp       # node-gyp rebuild for the *current* Node ABI only; output goes to build_log.txt, never fails the install
npm run clean           # deletes dist/bindings/* (all committed binaries!) -- don't run casually
```

Tests bind ports 3000 (ws) and 3001 (wss, certs in `tests/certs/`). The test file currently iterates only `['Non-SSL']`; the SSL loop is wired up but disabled. `tests/autobahn-*.js` are manual Autobahn testsuite harnesses, not part of `npm test`.

### Building the release binaries (multi-ABI)

`binding.gyp` is only used by `npm install` for a local build against the running Node (Node's zlib, no zlib-ng), and only when `scripts/install.js` finds no prebuilt binding for the platform/ABI (`CWS_FORCE_BUILD=1` overrides); it must carry the same include path and defines as the Makefile or it fails silently (the install script discards the exit code). Release binaries are built by the `Makefile` (macOS/Linux) and `make.bat` (Windows), which:

1. Download official Node header tarballs for one pinned version per supported major into `targets/` (`VER_115`=Node 20, `VER_127`=Node 22, `VER_137`=Node 24, `VER_147`=Node 26; the number is the Node ABI / `process.versions.modules`).
2. Compile `src/*.cpp` once per ABI with `g++`/`cl` directly, with `-I src/headers/$V` for the matching Node major.
3. Build the vendored zlib-ng (`deps/zlib-ng`, native `zng_` API) once per OS/arch: CMake into `deps/zlib-ng/build-<OS>-<arch>/` on macOS/Linux, `nmake -f win32\Makefile.msc` on Windows. The bindings are compiled with `-DCWS_ZLIB_NG` and link it statically. `src/MicroDeflate.h` is a self-contained fixed-Huffman DEFLATE encoder used for independent messages (shared mode) via `zlib::deflateIndependent` (greedy LZ77 over a 13-bit hash table whose entries pack an 8-bit tag above a 24-bit position+1 so the candidate test is one subtraction and compare, literals handled in pairs in an inner loop, SSE2 32-byte match head with a portable fallback, precomputed length-symbol and distance tables, stored-block fallback when the input does not compress; messages of 8 MB or more clear the table before and after; `microdeflate::Window` reuses the same `encodeSpan` loop with a per-connection 48 KB buffer (32 KB history + 16 KB append margin, slide = memmove + entry rebase) and a 12-bit table: `zlib::createDeflate(level <= 1)` returns a `Stream` wrapping it when microdeflate is enabled, so `dedicated` mode at level 1 is microdeflate takeover (64 KB per connection, RPC capture 2.84x shared -> 3.50x) and level 2+ stays zlib-ng; table bits 12/13/14 measured 3.50/3.55/3.57, the rest of the gap to zlib's fixed-tree takeover (3.82x) is chained matching; `Window::append` extends the history without indexing, used by `Queue::Message::windowSync` entries (zero wire bytes; prefix in the message, payload via `syncBody`) that `sendShared` queues behind a spliced prepared message on a microdeflate-takeover socket so the window stays in step with the client (`prepareSend` and `WebSocket::materialize` apply them in queue order; with the worker off `sendShared` appends immediately because compressed sends are deflated at send time); zero-length entries are popped by `consumeSent`/`sendComplete` regardless of bytes sent; output must stay byte-identical across speed work, and speed claims need the production EPYC, not only Apple silicon: gcc/Zen and clang/M-series disagreed on every layout change in 4.11.2, only the hybrid bit-writer flush won on both; the 4.14.0 restructuring came from two sub-agent reviews with the scratchpad kit `mdkit2/` (`run_epyc.sh`, `perf_epyc.sh`, `asm_epyc.sh`): tagged 24-bit positions, literal pairs, SSE2 match head, packed tables, -20% on the EPYC); Measured and rejected on the RPC capture, so do not retry without new data: dynamic Huffman trees per block (+9.4% ratio at 2.4x the time on EPYC), two candidates per hash slot (+2.5% at 1.5x), 3-byte minimum matches (worse ratio), packed 32 KB table with 16-bit tags (gcc partial-register stalls on Zen), single-branch candidate check (unconditional random load), `__restrict`, 12/14-bit tables. libdeflate level 1 reaches 3.28 vs our 2.86 at 2.6x the time; `src/Zlib.cpp` is the only file that includes a zlib header; without the define (node-gyp fallback) it uses Node's zlib. `src/MicroInflate.h` is the matching decoder for client messages (single-shot, 10-bit primary table + subtables built in one pass, 64-bit bit buffer, BMI1/2 runtime dispatch on x86-64, portable elsewhere, ~12 KB stack, no allocation): `zlib::inflate` tries it into the hub's scratch buffer first and falls back to zlib-ng for anything it declines (output above the buffer or `maxPayload`, invalid input); `CWS_MICRO_INFLATE=0` disables it. It may scribble up to ~290 bytes past the returned length inside `outCap`. Benchmark/fuzz kit: scratchpad `inflate/` (`run_epyc.sh` builds zlib-ng, libdeflate and the decoder on the EPYC; `fuzz.cpp` is a differential fuzz against zlib). EPYC, 2 KB browser messages: zlib-ng 3.31 µs, libdeflate 3.11, microinflate 2.25; the table build was the cost, not the decode loop. Real Chrome streams (scratchpad `inflate/chrome/capture.js` + `page.html`: a capture server that does the upgrade like cWS and records each compressed payload with its original; run via the Claude-in-Chrome tab at http://localhost:3460): EPYC zlib-ng 8.34 / libdeflate 7.20 / microinflate 5.93 µs per 5.3 KB message; Chrome offers `permessage-deflate; client_max_window_bits`, sends dynamic trees at ~2.9x and does not fragment. In the server receive path on the EPYC a compressed 2 KB message costs 5.11 -> 3.38 µs of JS-thread CPU (203k -> 307k messages/s per core); Apple silicon 4.50 -> 2.46.
4. Emit `dist/bindings/cws_<platform>_<arch>_node<ABI>.node`.

```sh
make                                  # all four ABIs for the host OS/arch (needs curl, cmake, g++/clang)
./build-on-docker.sh linux/arm64      # Linux arm64 (native on Apple Silicon, ~1 min)
./build-on-docker.sh linux/amd64      # Linux x64 (default; emulated on Apple Silicon, slower)
make.bat                              # Windows x64; auto-detects VS 2022 (Build Tools or any edition)
```

All of it can be driven from the Mac. Docker builds mount the repo and write straight into `dist/bindings/`. The Windows build runs in the Parallels "Windows 11" VM through the shared folder (cmd refuses UNC batch paths, hence `pushd`):

```sh
prlctl resume "Windows 11"
prlctl exec "Windows 11" cmd /c "pushd \\\\Mac\\code\\cWS && make.bat"   # 4 backslashes in zsh -> \\Mac
prlctl suspend "Windows 11"
```

The VM is Windows on ARM: `vcvars64` still emits x64 code, so `make.bat` names outputs `win32_x64` explicitly, and testing them needs an x64 Node in the guest (an x64 zip from nodejs.org extracted under `C:\Temp` works; the guest's own ARM64 Node cannot load them). Docker base image is Ubuntu 22.04 = the minimum glibc baseline. Smoke-test a binding on its target Node with `node node_modules/mocha/bin/mocha -r ts-node/register 'tests/**/*.test.ts' --exit`, e.g. inside `node:22-bookworm` for Linux.

Adding a new Node major means: add a `VER_xxx`/ABI line to `Makefile` and `make.bat`, vendor that Node version's private headers into `src/headers/<major>/`, and add a `#if NODE_MAJOR_VERSION==<major>` include block in `src/Addon.h`. Vendoring = copy every `src/**/*.h` from the Node source tarball, plus `deps/ncrypto/ncrypto.h` and any `deps/v8/include/*.h` missing from the official headers tarball, then make `ssl_` public in `crypto/crypto_tls.h` (`TLSWrapSSLGetter` needs it). For 26 there is a second edit: `MaybeStackBuffer::AllocateSufficientStorage` (primary and the concept-constrained `V8Type` partial specialization) and `ToPath` are defined in-class in `util.h` instead of out-of-line in `util-inl.h`, because MSVC `cl.exe` cannot match out-of-line member definitions once that constrained specialization exists (Node builds Windows with clang-cl, which the Parallels VM does not have). Both edits are marked with a `cWS:` comment. Node's gyp-only config macros (e.g. `HAVE_SQLITE`, `HAVE_AMARO` for 26) must be defined before the include. Expect V8 API churn in `Addon.h` on each major; 26 needed tagged internal-field reads (`BaseObject::FromJSObject`) and dropped `Object::GetIsolate` and the `MakeCallback` overload without `async_context`.

## Architecture

### Two layers, one binary

- **`lib/*.ts` (thin JS facade)** compiled to `dist/`. `shared.ts` loads the native addon by filename `cws_${platform}_${arch}_node${versions.modules}` and wires native group callbacks (`onConnection`, `onMessage`, `onDisconnection`, …) to per-socket `registeredEvents`. Events are single-listener: `on()` overwrites, with a console warning. `client.ts` exports `WebSocket` (used for both client sockets and server-side peers, distinguished by `options.external`), `server.ts` exports `WebSocketServer` (aliased as `WebSocket.Server`).
- **`src/` (C++ addon)** is the uWebSockets 0.14 core (`Hub`, `Group`, `WebSocket`, `HTTPSocket`, `Networking`, `WebSocketProtocol.h`, `Extensions` for permessage-deflate) plus the V8 binding layer in `src/Addon.h` / `Addon.cpp`. `Backend.h` picks the event backend: libuv everywhere (`-DUSE_LIBUV` is always set), the epoll backend in `Epoll.*` is legacy and not compiled in by the Makefile.

### How a server connection gets into C++ (the important part)

cWS does **not** run its own HTTP listener. `WebSocketServer` uses a Node `http`/`https` server (user-supplied or created internally) and hooks its `'upgrade'` event. In `upgradeConnection()`:

1. It grabs the raw libuv handle from the Node socket (`socket._handle`, or `_parent._handle` for TLS).
2. For TLS it calls `native.getSSLContext(socket.ssl)` to pull the raw `SSL*` out of Node's internal `TLSWrap`. This is why `src/headers/<major>/` vendors Node **private** headers (`crypto/crypto_tls.h`, `base_object-inl.h`, etc.) and `Addon.h` defines `NODE_WANT_INTERNALS` around them: `TLSWrapSSLGetter` subclasses `node::crypto::TLSWrap` to reach the protected `ssl_` member. This is the ABI-fragile part and the reason binaries are per-Node-major.
3. `native.transfer(fd, ssl)` creates a `Ticket` and the Node socket is destroyed. On its `'close'` event, `native.upgrade(group, ticket, secKey, extensions, protocol)` hands the fd to the uWS `Hub`, which performs the WebSocket handshake and owns the socket from then on. On Linux with Node >= 20 the fd is `dup()`ed first as a workaround for io_uring (see comment in `Addon.h`).

`noServer: true` + `handleUpgrade()` follows the same path for `ws` compatibility. `path` and `verifyClient` checks happen in JS before the transfer.

### Client connections

The client side never touches Node sockets: `native.connect(clientGroup, url, ws)` lets the uWS `Hub` do TCP/TLS itself using a process-wide `SSL_CTX` created in `cSNode.cpp` (TLS 1.0–1.2 only). `secureProtocol = 'TLSv1_2_method'` is exported for users to pin their https server to match.

### Write corking

`Socket::sendTransformed` does not write when the socket is corkable (WebSockets only, plain TCP only) and `NodeData::corkState->enabled` is set. It frames the message into the socket's `messageQueue` and registers the socket in the per-loop `corkState->pending` list. `Socket::flushCorked` drains that list with one `sendmsg`/`WSASend` gather per socket from two libuv hooks registered in `registerCheck` (`src/Addon.h`): a `uv_prepare` (before the loop blocks in poll) and the existing `uv_check` (after poll and after Node's immediates). Anything that cannot be written falls through to the normal `UV_WRITABLE` drain loop in `ioHandler`. `closeSocket`/`onEnd`/`transfer` call `flushCorkedOnClose`, which unregisters the socket and pushes what it can to the kernel without invoking callbacks. `CWS_CORK=0` disables it at addon load (`corkEnabledFromEnv`). `HttpSocket` is never corkable because `Hub::upgrade` deletes it synchronously.

### Slab messages (corked sends)

`Socket::sendTransformed` on the corked path appends a plain frame to the slab at the queue tail (`slabWithSpace`, a `NodeData::slabSize` = 16 KB pool block with inline data and `Message::run = true`) instead of allocating a block per send; a frame with a callback, a frame larger than a slab, a prepared payload's borrowed segment and a compress-pending message get their own `Message`, and the next plain send opens a new slab after them. Only the main thread touches the tail and a message inside a worker op is never the tail (`submitToWorker` unlinks it), so appending never races the worker; after a partial write `data`/`length` describe the unsent part and the append position is still `data + length`. `sendShared` writes its header + prefix into the slab too, and a body of up to 4 KB (`INLINE_BODY_MAX`, which every compressed blob satisfies) is copied in after it when there is no callback; only larger bodies are borrowed. Compression throughput: one worker thread deflates about 200k 2 KB messages/s (microdeflate at ~2 µs/KB), so per-send compression at higher rates backs up onto the JS thread; prepared messages compress once per emission and are unaffected. If per-send compression at scale ever matters, shard sockets across several worker threads (per-socket ordering survives a hash-based shard); not done. Measured on the EPYC: fan-out 2 KB 0.65 -> 0.45 µs JS thread per delivery, 1.5M 256 B sends/s 40% -> 26%.

### Send worker thread

`SendWorker` (`src/SendWorker.cpp`) starts one `std::thread` at addon load when corking is enabled. `Socket::uncork` moves up to 512 queued frames into a `Socket::SendOp` (ownership moves with them; ops come from a main-thread freelist, `allocOp`/`freeOp`) and hands it over through `deps/readerwriterqueue` (plain SPSC queues both ways). The worker only calls `sendmsg`/`WSASend` and fills `result`/`error`; `Socket::sendComplete` on the main thread pops what was sent (blocks go back to the per-class freelist untouched), requeues the rest at the head, resubmits if more queued, arms `UV_WRITABLE` for the classic drain loop on a short write, runs send callbacks, and calls `endCb` (= `STATE::onEnd`, set in `setState`) on a hard error. While an op is in flight `write()` appends to the queue and the drain loop stays out. `closeSocket` orphans an in-flight op (`socket = nullptr`, `closeFd = true`) and lets the completion close the fd, so a reused fd number can never receive the old socket's bytes. SSL sockets never use the worker. `CWS_SEND_THREAD=0` disables.

Hand-offs are batched per loop iteration: `submit` only enqueues, `SendWorker::flush` (end of `flushCorked` in both hooks, and after draining completions) signals the worker's semaphore once, and only if the worker is asleep (`workerSleeping`, Dekker-style with a seq_cst fence on both sides; the worker spins `CWS_SEND_THREAD_SPIN_US`, default 50, before sleeping). Completions are drained in the hooks: `beforePoll` (end of the prepare hook) sets `loopIdle`, fences, and drains once more; `afterPoll` (start of the check hook) clears it and drains; the worker calls `uv_async_send` only when it sees `loopIdle`, so a busy loop never touches the eventfd. Keep both Dekker pairs intact when editing: dropping a fence turns a lost wake into a stalled socket. A completion only wakes an idle loop when it needs prompt handling: partial write, error, a message with a callback (`op->hasCallback`, set by the worker while gathering) or `op->needWake` (set on the main thread by `closeSocket` orphaning the op, by `write()` while `sendBusy()`, and by `uncork()` returning early because an op is in flight); a clean completion parks in `toMain` until the loop's next natural wake (`getBufferedAmount` is stale meanwhile, which is harmless since reading it means the loop is awake and `afterPoll` drained first). `drainCompletions` dequeues up to 64 ops and prefetches them before running `sendComplete`. The `ioHandler` `UV_WRITABLE` branch hands a stalled socket to the worker (`submitToWorker`) rather than draining on the JS thread; the synchronous fallback is `writeQueueGathered` + `consumeSent` with no cork toggles. Measured 2026-09-03 on the production EPYC 9454P (JS thread µs, worker off -> on): echo 64 B 7.35 -> 5.30, echo 4 KB 13.25 -> 9.65, fan-out 256 B to 50 sockets 0.70 -> 0.40, 2 KB 1.50 -> 0.97; a 120 fps render loop keeps every frame under 1 ms at 384k 2 KB sends/s with the worker, drops frames without. Whole-process CPU is higher with the worker (hand-off + spin). Speed claims for the worker need the EPYC, not Apple silicon: syscalls there cost several µs (SRSO Safe RET; Docker seccomp measured irrelevant). On Linux the worker follows the JS thread's L3 domain (`followJsThread`: `jsCpu` recorded in `flush`, re-pin after a batch when it changed; `CWS_SEND_THREAD_AFFINITY=0` disables): fan-out 2 KB 0.95 -> 0.65 µs, render loop at 384k sends/s 47% -> 21% JS thread. Rejected with measurements: io_uring in the worker (nothing on the JS thread, SQPOLL burns a core), worker-side freeing of message blocks (cross-thread malloc contention collapsed at 1.5M sends/s; the freelist replaced it), a 20 ms spin budget (no change), confining the JS thread to its L3 domain (no change; the halving seen with a two-core cpuset came from co-locating the benchmark client, which does not apply to NIC traffic). All items from the 2026-09-03 reviews have shipped (slab messages in 4.13.0; clean-completion parking, batched drains, worker-side stalled drains and the compressed-path arena in 4.14.0). Not done, low value: fast API calls for `send` (~20% of a 0.26 µs call), a batched fan-out native call (prepared messages already cover the copy), `TCP_NOTSENT_LOWAT` on drawing sockets (only useful with app-level frame dropping). Benchmark harness: scratchpad `linuxbench/` (`bench_cpu.js`, `cpu_fanout.js`, `jitter_cli.js` + `jitter_srv.js`), run in a `node:24-bookworm` container on iris2 for per-thread CPU via `/proc/thread-self/stat`.

Compressed sends: `WebSocket::send` queues the raw payload as a `compressPending` message (`enqueueCompressPending`: raw inline in a pool block, or on the heap in `Message::rawOwned` above 16 KB; the main thread frees both); `prepareSend` deflates + frames it on the worker with the socket's window (`op->deflateWindow`) or the worker's own shared compressor into the op's scratch arena (`op->scratch`, grown in place with frame pointers rebased, `Message::inScratch`), then builds the iovecs. `unscratch` copies a partially sent scratch frame to the heap before `requeueFront`, since the op is reused. Any main-thread write path calls `materializePending()` first (`WebSocket::materialize` via `materializeCb`, using the hub's compressor). A socket closed mid-flight hands its window to the op (`destroyWindow`, `workerOwnsWindow`) so `onEnd` does not free it under the worker.

### Receive worker thread (optional)

`RecvWorker` (`src/RecvWorker.cpp`, default off; `receiveThread: true` per server, `CWS_RECV_THREAD=1`/`0` overrides for every server) is one thread per loop, started lazily by the first group that asks for it, that owns **readability** of plain-TCP server WebSockets (SSL and client sockets always stay on the loop; Windows compiles the stubs and ignores the option). `Hub::upgrade` calls `WebSocket::attachRecvWorker`, which stops the uv_poll (`baseEvents = 0`; the handle is only armed for `UV_WRITABLE` while a write is stalled, so every `setPoll(UV_READABLE)` in the send paths became `setPoll(baseEvents)`) and registers the fd with the worker. The worker polls with epoll/kqueue, does `recv`, drives `WebSocketProtocol<SERVER, RecvConn>` (the same parser, with an Impl that mirrors `WebSocket::handleFragment` including fragment/control-tip reassembly, `maxPayload`, UTF-8 validation and inflate through its own `zlib::inflate` stream and scratch), and appends records to a ring in plain native memory (`CWS_RECV_RING_KB`, default 8 MB, power of two). Record = 16-byte header `{u32 length, u8 type, u8 opCode, u8 flags, u8 pad, void *socket}` + payload padded to 16; length `0xffffffff` is a wrap marker; a record is at most half the ring, larger payloads (and anything while the ring is full) are heap copies referenced by an `F_HEAP` record and freed by the drain. Types: MESSAGE, PING, PONG, CLOSE (raw close payload, parsed on the main thread), EOF, ERROR (recv error or a protocol violation the parser would have force-closed), ACK. The worker never writes to a socket and never closes an fd: the drain (`RecvWorker::drain`, called from `beforePoll`/`afterPoll` in the same hooks as the send worker, in batches of 64 inside `readBatchHook` = the read scope) runs the existing main-thread code: `messageHandler` with zero-copy views over the ring (detached before the read index advances), `send(PONG)` + `pingHandler`, `pongHandler`, `WebSocket::close(parseClosePayload(...))`, and `WebSocket::onEnd` for EOF/ERROR; records for a closed or shutting-down socket are dropped. Close quiesces: `closeSocket` on an attached socket does not close the fd; it enqueues DEREGISTER, the worker removes the fd from its poller and answers with ACK, and `Socket::recvDeregistered` releases the fd through `FdRelease` (shared with an orphaned send op: last holder closes) and deletes the object once libuv's close callback has also run (`recvUvClosed`/`recvAcked`). Backpressure: a record that does not fit parks the socket (EPOLLIN off / EV_DISABLE, per-socket deferred list in order, `recvStalls`), sets `needResume`; the drain, after freeing space, sends RESUME. Wake protocol: main -> worker requests in an SPSC queue, the worker blocks in its poller with `workerSleeping` set (Dekker; main writes the wake eventfd/pipe only if it sees the flag); worker -> main via `uv_async_send` only when it sees `loopIdle` (set in the prepare hook after a final drain, cleared in the check hook), with the Dekker fences on both sides. Do not try to skip `loopIdle` with `uv_backend_timeout()`: the public function returns 0 whenever io watcher changes are queued (which `flushCorked` just did), not only when the poll will not block; that lost wakes for a full timer period. The async handle is ref'd while sockets are attached so the process stays alive like it did with active poll handles. Stats: `recvWorkerWakes`, `recvWorkerMessages`, `recvStalls`. `Socket::transfer` (cross-loop group transfer, not reachable from the JS API) does not know about the worker. Tests: `receive worker thread` block in `tests/server-client.test.ts` (`tests/recv-thread.child.js` for the ring-size cases). Whole-process CPU goes up (the worker pays epoll + recv per frame); it pays off when the JS thread is the bottleneck.

### Prepared (shared) messages

`cWS::SharedPayload` (`src/WebSocket.h`) holds one payload for many recipients: the raw bytes plus, after the first compressed send, their deflate blocks (`Hub::deflate` with no window, i.e. the shared compressor; sync-flush tail stripped like every compressed message). `WebSocket::sendShared(prefix, payload, ...)` queues one frame as two `Queue::Message`s: an owned one with the frame header and the prefix, and a borrowed one (`ownsData = false`) pointing into the payload whose completion callback (`sharedSent`) drops the payload reference and then runs the user's callback. Compressed, the prefix becomes DEFLATE stored blocks (`00 LEN NLEN`, BFINAL=0) ahead of the cached blocks; that is only valid without context takeover, so a socket with a `slidingDeflateWindow`, the client role (masking) and an empty payload fall back to a contiguous `send()`. JS: `PreparedMessage` (`lib/prepared.ts`, native handle released through a `FinalizationRegistry`) and `WebSocket.send` routes a `PreparedMessage` (with the optional `prefix` option) to `native.sendShared`.

### Things that are easy to get wrong

- `dist/*.js` and `dist/bindings/*.node` are committed. Rebuild TS with `npm run build-ts` and commit the output; binaries must be rebuilt on each platform when C++ changes.
- Binary messages reach JS as an `ArrayBuffer` that is a zero-copy view over the per-loop receive buffer shared by every socket. `onMessage` in `Addon.h` detaches it after the handler returns, so retaining it without `slice()` throws on later use rather than exposing another connection's bytes. Text frames are copied into a V8 string. Ping/pong payloads also go through the string path.
- Message delivery: `NodeData::readHook` (set by `installReadScope` in `Addon.h` at group creation, `CWS_READ_SCOPE=0` disables) wraps every socket read in one `node::CallbackScope`; inside it `onMessage` invokes the handler with a plain `Function::Call` (handles live in the read's `HandleScope`, no per-message scope or microtask drain) and collects the binary `ArrayBuffer` views in a per-read vector that is detached after the scope closes, i.e. after nextTick/microtasks drained. So a continuation resolving in the drain still sees the bytes, a view from an earlier message of the same read is readable during a later message's handler, and anything that waits on real I/O sees a detached buffer. Microtasks drain per read, as with `ws`. With the hook off, the old path (`node::MakeCallback` per message, detach right after the handler) runs. Other handlers (ping/pong/close/connection) still go through `MakeCallback`, nested inside the read scope when they fire during a read. A/B harness: scratchpad `recv/ab.sh` (server CPU per message for sizes x frames-per-read); `stats.messagesIn / stats.reads` is the frames-per-read a socket class sees in production.
- Receive-side experiments, measured 2026-09-05 on the EPYC (JS-thread µs per message, one frame per write unless noted, kits in scratchpad `recvring/` and `recvuring/` with reports and reproducible `run_epyc.sh`): (1) a native receive THREAD delivering parsed, inflated messages through a SharedArrayBuffer ring (Dekker wake protocol like the send worker): JS thread 5.9 -> 3.0 (88 B compressed), 6.6 -> 3.9 (2 KB compressed), 5.8 -> 3.6 (120 B), 6.3 -> 5.8 (2 KB), 0.8 -> 0.7 (120 B x8 per write), 0.8 -> 0.2 zero-copy (2 KB x512); but +5-7 µs of worker CPU per message (its own epoll+recv+eventfd), a loop wake per 1.5-4 messages remains, +5 µs median latency for the hop, and SAB views cannot be detached so delivery must copy. Verdict: only worth it when the JS thread is the bottleneck with spare cores; inflate-only offload is the separable piece; the batched-scope delivery it used is what 4.16.0 adopted. (2) MAIN-THREAD io_uring multishot recv with provided buffer rings (kernel 6.8, liburing 2.3, needs `--security-opt seccomp=unconfined`; DEFER_TASKRUN needs the eventfd, which fires twice per message when idle): 5.9 -> 6.3 defer / 5.1 coop (88 B compressed), 6.6 -> 7.4 / 7.0 (2 KB compressed), batched shapes +0.1-0.2 (a 16 KB CQE carries fewer frames than one large recv), idle +4-10 µs; the recv syscall goes away but the kernel copy and re-arm run on the JS thread as task work and the wake stays. Verdict: no gain on 6.8; revisit only with 6.10+ recv bundles / incremental buffer consumption and a non-eventfd wake. Do not retry either without new data. Wake-cost floors measured 2026-09-05 on the EPYC (kits: scratchpad `kernel-ideas/wake.c`, `runtime-ideas/loopcost.cc`): waking a sleeping thread costs 3.5-5 µs of the wakee's CPU in the kernel (scheduler + C-state exit; 8-11 µs when the wake arrives through TCP, 10-19 µs on a cold core at sparse rates because C2 exit and the low P-state are charged to the wakee), a full Node/libuv iteration is 0.62 µs, syscall floor 0.26 µs, a cross-CCD atomic 0.19 µs; MakeCallback vs Function::Call within noise once per batch. So the 6-7 µs per one-frame-per-read message is ~1 µs of work plus an amortised kernel wake, and nothing in user space makes a wake cheaper: only fewer wakes (batching, latency), warmer cores (`/dev/cpu_dma_latency`=0 halved the wake at sparse rates, host-level), or a spinning core. Measured and rejected: spinning on the JS thread (CPU per message equals the arrival interval), NAPI/socket busy polling (no NAPI id behind Docker's bridge/veth, per-epoll params need 6.9), SRSO off (~0.5 µs/msg, host-wide), timer slack (nothing sleeps sub-ms), Atomics.waitAsync and postMessage as wake sources (0.8-1.7 µs worse than uv_async), uv_poll on an eventfd (0.4 µs worse), fast API calls and loop-phase trimming (≤0.5 µs total). Open, not built: per-group frame-gated delivery (read + deliver, `uv_poll_stop`, re-arm from one shared timer every T ms: 6 -> ~2.4 µs/msg at T=2 ms for the drawing shape, up to T latency); steering the JS thread to the NIC softirq's L3 (`SO_INCOMING_CPU` + `sched_setaffinity`, 0.7-1.5 µs/msg in isolation); a context-aware addon for worker_threads scale-out (per-Environment hub/hooks/send worker with `AddEnvironmentCleanupHook`; multiplies capacity, does not lower per-message cost; `SharedPayload` could serve subscribers across isolates).
